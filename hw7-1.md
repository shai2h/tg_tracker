# Домашка 7-1 — Итеративная архитектура: переосмысление очереди уведомлений

## Контекст

На уроке мы рефакторили обработку фоновой классификации и обсуждали три варианта
доставки результата в бот:

**Вариант 1 — asyncio.Future** (что было до урока)
`category_future` создавался в хендлере и передавался в сервис. Middleware ждал
результата. Проблема: aiogram-деталь протекла в доменный сервис, REST API
передавал `None` делая вид что это нормально.

**Вариант 2 — колбэки** (что сделали на уроке)
`notify` и `notify_error` определяются в хендлере, передаются через
`service.create()` → `queue.enqueue()` → замыкание `on_done`. Граница слоёв
формально соблюдена — бот-логика живёт в бот-слое. Но два колбэка пробрасываются
через три слоя уже на первом коммите. Это классический запах callback hell —
не сейчас, но через пару фич.

**Вариант 3 — две очереди** (идея с урока, не реализована)
Сервис получает две абстрактные очереди: одну для классификации, одну для
уведомлений. Сервис оркестрирует — он решает что и когда писать в очередь
уведомлений. Хендлер тупой: читает из очереди уведомлений и отправляет
пользователю.

Все три варианта валидны. У каждого есть плюсы и минусы. Главное — не нарушать
границы слоёв. Этот итеративный процесс — переосмыслить, передумать, переделать
лучше — и есть нормальная инженерная работа.

**Задача этой домашки** — сначала написать интеграционные тесты на текущий код,
а потом провести рефакторинг так чтобы тесты остались зелёными без изменений.

## Часть 0. Интеграционные тесты — до рефакторинга

Смысл этого задания в том, что хороший интеграционный тест тестирует **поведение**,
а не реализацию. Когда тест проходит до и после рефакторинга без изменений —
это и есть признак что тест написан на правильном уровне.

### Что мокаем

Только LLM-провайдер — самая внешняя граница. Всё остальное реальное:

После того как все 4 теста зелёные на текущем коде — **не меняй их**. Они должны
пройти снова после рефакторинга в частях 1–3 без единого изменения в тестах.
Если пришлось менять тест — значит тест был написан на реализацию, а не на поведение.

## Часть 1. Очередь уведомлений

### Идея

Сейчас бизнес-логика уведомлений размазана:
- `confidence < 0.6` → решение в сервисе, но текст сообщения нигде
- таймауты → в хендлере
- "Всё ещё определяю..." → в хендлере

С двумя очередями сервис становится единственным местом где принимаются решения.
Хендлер только читает и шлёт.

### 1.1 Модель уведомления

Создай `app/bot/notifications.py`:

```python
from dataclasses import dataclass
from enum import Enum

class NotificationKind(Enum):
    CLASSIFIED = "classified"           # успешно, confidence >= 0.6
    LOW_CONFIDENCE = "low_confidence"   # confidence < 0.6
    FAILED = "failed"                   # классификатор упал

@dataclass
class ClassificationNotification:
    kind: NotificationKind
    category: str | None = None
    confidence: float | None = None
```

### 1.2 Абстрактная очередь уведомлений

В `app/bot/notifications.py` добавь Protocol:

```python
from typing import Protocol

class NotificationQueue(Protocol):
    async def put(self, notification: ClassificationNotification) -> None: ...
    async def get(self) -> ClassificationNotification: ...
```

### 1.3 Реализация — asyncio.Queue

Там же:

```python
class InMemoryNotificationQueue:
    def __init__(self) -> None:
        self._queue: asyncio.Queue[ClassificationNotification] = asyncio.Queue()

    async def put(self, notification: ClassificationNotification) -> None:
        await self._queue.put(notification)

    async def get(self) -> ClassificationNotification:
        return await self._queue.get()
```

## Часть 2. Сервис — оркестратор

### 2.1 Убрать колбэки из service.create()

Сигнатура меняется — вместо `notify` и `notify_error` принимает очередь уведомлений:

```python
async def create(
    self,
    telegram_id: int,
    username: str | None,
    data: ExpenseCreate,
    notification_queue: NotificationQueue | None = None,
) -> ExpenseOrm:
```

### 2.2 Бизнес-логика уведомлений в on_done / on_error

Сервис сам решает что писать в очередь:

```python
async def on_done(category: str, confidence: float) -> None:
    stored = category if confidence >= _LOW_CONFIDENCE_THRESHOLD else _LOW_CONFIDENCE_CATEGORY
    async with self._session_factory() as session:
        await ExpenseRepository(session).update_category(expense_id, stored)
        await session.commit()
    if notification_queue is not None:
        if confidence >= _LOW_CONFIDENCE_THRESHOLD:
            await notification_queue.put(
                ClassificationNotification(
                    kind=NotificationKind.CLASSIFIED,
                    category=stored,
                    confidence=confidence,
                )
            )
        else:
            await notification_queue.put(
                ClassificationNotification(kind=NotificationKind.LOW_CONFIDENCE)
            )

async def on_error(exc: Exception) -> None:
    if notification_queue is not None:
        await notification_queue.put(
            ClassificationNotification(kind=NotificationKind.FAILED)
        )
```

## Часть 3. Хендлер — просто читает и шлёт

### 3.1 add_expense

Хендлер создаёт очередь, передаёт в сервис, ждёт результата через `asyncio.wait`:

```python
notification_queue = InMemoryNotificationQueue()

await service.create(..., notification_queue=notification_queue)
await message.answer(f"Сохранил: {title} — {amount} ₽\nОпределяю категорию...")

done, pending = await asyncio.wait(
    {asyncio.ensure_future(notification_queue.get())},
    timeout=_CATEGORY_FIRST_TIMEOUT,
)

if pending:
    await message.answer("Всё ещё определяю категорию, нужно чуть больше времени...")
    done, pending = await asyncio.wait(pending, timeout=_CATEGORY_HARD_TIMEOUT)
    if pending:
        # воркер не успел — молчим, пользователь увидит в /list
        for task in pending:
            task.cancel()
        return

notification: ClassificationNotification = done.pop().result()
```

### 3.2 Отправка по типу уведомления

```python
match notification.kind:
    case NotificationKind.CLASSIFIED:
        await message.answer(f"Категория: {notification.category} ✓")
    case NotificationKind.LOW_CONFIDENCE:
        await message.answer("Не удалось узнать категорию")
    case NotificationKind.FAILED:
        await message.answer("Не удалось определить категорию")
```

Хендлер не знает про `confidence`, не знает про `_LOW_CONFIDENCE_THRESHOLD` —
это всё решено в сервисе.

### Inline keyboard при низкой уверенности

Сейчас при `confidence < 0.6` пользователь получает "Не удалось узнать категорию"
и на этом всё. Сделай лучше: отправь inline-клавиатуру "Похоже это «транспорт» —
верно?" с кнопками **Да** / **Нет, другое**. При "Нет" — показать список категорий
кнопками, пользователь выбирает сам. Сохранить выбор через `repository.update_category`.

`StatesGroup` — всё это есть в aiogram. FSM-состояния вынеси в `app/bot/states.py`.
